Scalability

⚡ Real problem

Your Laravel API is fast in staging. It ships to production.

Traffic grows.

100 req/sec → fine 1 000 req/sec → slowdown felt 10 000 req/sec → p95 explodes

CPU at 90%. PostgreSQL connections full. Redis sometimes slow.

The user says one thing: "The site is slow."

Scalability starts here. It is not "add more servers." It is being able to see which part breaks first as load grows.

Mental model — every request is a journey

User→ Nginx→ PHP-FPM→ Redis→ Postgres→ SMS API
Each layer has a limit. The smallest limit becomes the whole system's limit.

Nginx connection limit. FPM worker count. DB connection pool. Redis memory. External API timeout.

Scalability = find the narrowest point on the request path.

Throughput vs latency

Throughput work per second → req/sec, jobs/sec Latency time for one item → 120ms, 800ms, 4s

Not the same. A system can accept 10,000 req/sec and still be bad if every user waits 5 seconds.

Why p95 matters

Average lies. It hides the slow tail.

p50 half of users faster than this p95 1 in 20 users is slower than this p99 1 in 100 — thousands of people at scale
◆ Rule

When p95 rises, production is hurting — even if the average looks fine. Watch percentiles, not averages.

Vertical vs horizontal

Vertical (scale up) — a bigger machine (4 CPU → 32 CPU, 8GB → 64GB). Simple, no architecture change, and often enough. But it has a hard ceiling (the biggest instance money can buy), the price is non-linear, and it stays a single point of failure — one machine, one fate.

Horizontal (scale out) — more machines behind a load balancer. No ceiling, and redundancy for free (one dies, others serve). This is the production path — but it demands one thing: stateless app servers (next lesson), because a request may land on any machine.

Vertical simple · fast · has a ceiling · single failure point Horizontal unlimited · redundant · needs stateless design · adds ops complexity
▲ The hidden bottleneck: DB connections

Scale app servers to 10 and each opens 20 DB connections — that's 200. If Postgres max_connections = 100, your own app DDoSes the database. Horizontal scaling shifts the bottleneck to shared resources (DB, cache). Put a connection pooler (PgBouncer) between app and DB.

text · the pooler fixes the fan-in10 app servers × 20 conns = 200  →  PgBouncer  →  Postgres (100 max)
◆ Don't over-engineer

Small traffic? Vertical scaling is fine — don't be ashamed of it. Making everything distributed on day one is textbook disease: you pay all the complexity, none of the benefit. Scale up first; scale out when a single box genuinely can't keep up.

Load Balancing

⚡ Real problem

You scaled your Laravel API from 1 server to 3.

Which server does a client hit? The client shouldn't know the server list. If one dies, the client shouldn't feel it.

Requests must enter one place and spread to healthy instances. That layer is the load balancer.

Load balancer skips the dead server and sends the request to a live one.

Algorithms

Round robin rotate evenly across servers Least connections send to the least-busy server IP hash same client → same server (sticky)

L4 vs L7 load balancing

L4 (transport) routes by IP + port only — fast, protocol-blind L7 (application) reads the HTTP request — can route by path, header, cookie

An L7 balancer (Nginx, HAProxy, ALB) can send /api to one pool and /admin to another, do TLS termination, and inspect requests. An L4 balancer just forwards packets — lower latency, but no HTTP awareness. Most web apps want L7.

Health checks

The LB pings each server on an interval (GET /health). No healthy reply within the timeout → the server is pulled from rotation. It recovers → automatically added back. Your /health endpoint should check real dependencies (DB, Redis reachable) but stay cheap — it runs constantly.

▲ Sticky sessions are a smell

IP-hash "stickiness" pins a user to one server so their in-memory session survives — but it breaks the moment that server dies (all its users are logged out), and it unbalances load (one heavy user, one hot server). The real fix is stateless servers (next lesson): move session to Redis, and any server can serve any request. Reach for stickiness only when you truly can't externalize state.

◆ Nginx = reverse proxy that load-balances
nginxupstream app {
    server 127.0.0.1:9000;   # App 1
    server 127.0.0.1:9001;   # App 2
    server 127.0.0.1:9002;   # App 3
}
server { location / { proxy_pass http://app; } }

Stateless Design

⚡ Real problem

User logs in — session saved in App 1's memory.

Their next request hits App 2. App 2 never heard of them. Logged out.

Horizontal scaling only works if any server can serve any request. That means no secret state in local memory.

Bad login session → App 1 RAM cart → App 1 memory upload progress → App 1 local disk Good session → Redis or signed cookie cart → database or Redis file → object storage (S3) progress → shared store
App 1App 2App 3 →RedisPostgres
Stateless apps point at shared state layers. Any app can serve any user.

Two ways to carry identity

Server-side session (in Redis) cookie holds only a session ID → server looks up state in Redis ✅ revoke instantly (delete the key) ✅ small cookie ❌ every request does a Redis lookup Stateless token (JWT) the token itself carries signed identity → server verifies signature, no lookup ✅ zero shared state, scales trivially ❌ can't revoke before expiry ❌ bigger, and stale until it expires

Both keep the app server stateless — the difference is where the state lives (shared Redis vs the token itself). Sessions favor control (instant logout); JWTs favor scale (no lookup). Many systems use short-lived JWTs + a refresh token to get both.

◆ Laravel

SESSION_DRIVER=redis, CACHE_STORE=redis, filesystem disk to S3. Now app servers hold nothing — kill one mid-traffic and no user notices. For token auth, Sanctum (SPA/mobile) or Passport (OAuth) issue and verify tokens.

Caching & Queues — When Each Enters

When cache enters

Cache is not a bandage for a slow DB. Cache is for data read often and changed rarely.

Good candidate Bad candidate GET /popular-news GET /balance GET /products/10 GET /payment-status GET /settings/public (stale = expensive here)

When a queue enters

Work that doesn't have to finish inside the request goes to the background.

API→return fast ·Queue→Worker→email / report / resize
Queue cuts user latency. It does not reduce total work — workers still do it.

The scaling path — in stages

100 req/sec one good server: indexes, slow-query log, timeouts, monitoring 1k req/sec more app instances + LB; sessions shared; DB pool matters 10k req/sec cache required; read replica; background jobs; hot endpoints split 100k req/sec CDN, sharding, event streaming, regional deploy, precompute
▲ The cache stampede

A hot cached key expires. In the same instant, 5,000 in-flight requests all miss and all run the expensive query together — a self-inflicted spike that can take the DB down. Mitigate with a short lock (first miss rebuilds, others wait), staggered TTLs, or refreshing the value slightly before it expires.

◆ Not all at once

Add each layer when a real bottleneck demands it — measured, not guessed. Premature caching hides bugs; premature sharding buys pain. Let the metrics (p95, DB CPU, queue depth) tell you what to add next.

CAP Theorem

In a distributed system, when the network splits, you get to keep two of three: Consistency, Availability, Partition-tolerance.

Consistency every read sees the latest write Availability every request gets a (non-error) response Partition tolerance system survives network splits
◆ The real choice is C vs A

Networks will partition — P is not optional. So the actual decision under a split: return maybe-stale data (choose A) or refuse to answer until consistent (choose C).

CP banks, inventory → refuse rather than serve wrong data AP feeds, likes, DNS → serve slightly stale, never go down
◆ Analogy

Two shop tills lose their link. CP = both stop selling the last item so it can't oversell. AP = both keep selling and reconcile later (maybe oversold). Money → CP. Instagram likes → AP.

PACELC — the fuller picture

CAP only describes behavior during a partition. PACELC adds: Else (when the network is fine) you still trade Latency vs Consistency. Waiting for every replica to confirm a write is consistent but slow; replying after one node is fast but may be stale.

during Partition: choose A or C Else (normal): choose L (latency) or C (consistency)
▲ "Consistency" means two different things

CAP's C (linearizability — every read sees the latest write) is not ACID's C (constraints hold). A database can be ACID-compliant and still be an AP system across nodes. Interviewers love this distinction — don't conflate them.

◆ Real systems tune per-operation

It's rarely all-or-nothing. Postgres is CP by default; Cassandra/DynamoDB let you pick a consistency level per query (ONE = fast/AP-ish, QUORUM = safer). You choose CP for a checkout, AP for a view counter — in the same app.

Consistency & Replication

Replication copies data to more machines — for read scale and survival. The cost: copies can lag.

Strong consistency read always sees latest write (slower, coordinated) Eventual consistency replicas converge after a delay (fast, may read stale)
▲ Read-your-writes trap

User updates their profile (write → primary), then reloads (read → replica that hasn't caught up) and sees the old value. Fix: route that user's reads to the primary for a moment, or read from primary after writes.

Sync vs async replication

Synchronous primary waits for replica to confirm before acking the write ✅ no data loss on failover ❌ slower writes Asynchronous primary acks immediately, ships to replicas after ✅ fast writes ❌ a crash can lose the last few writes (replication lag)

Most setups run async for speed and accept a tiny loss window. Financial systems use sync (or quorum) for the writes that must never vanish.

Failover

If the primary dies, a replica is promoted to primary. Automated tools (Patroni, RDS multi-AZ) detect the failure and repoint traffic. The gap between "primary dead" and "replica promoted" is downtime — and any un-replicated async writes are lost.

◆ Laravel

Configure separate read and write connections in config/database.php. Laravel routes writes to the primary and reads to replicas automatically — and stays "sticky" to the primary for the rest of a request after a write, sidestepping the read-your-writes trap.

SQL vs NoSQL

⚡ Real problem

"Just use MongoDB, it scales" — said before anyone asked what the data looks like.

Pick by data shape and access pattern, not hype.

SQL (Postgres/MySQL) relations, joins, transactions, strong schema → orders, payments, anything relational + consistent NoSQL document (Mongo) → flexible/nested, few joins key-value (Redis) → cache, sessions, counters wide-column → massive write throughput, time-series graph (Neo4j) → relationship-heavy (social, fraud)

Choose by access pattern, not by hype

Need joins, transactions, ad-hoc queries? → SQL Fixed key → value lookups, huge write volume? → key-value / wide-column Deeply nested docs, schema changes often? → document Traverse relationships (friends-of-friends)? → graph
◆ Default to SQL — and use its escape hatches

Most apps are relational. Postgres scales far further than people assume: read replicas, partitioning, and JSONB columns for the genuinely flexible bits (so you get schema-on-read inside a relational DB, indexed with GIN). Reach for a separate NoSQL store for a specific access pattern SQL handles poorly — not as a default, and rarely as your only database.

▲ "NoSQL scales" is half the story

NoSQL scales writes by dropping things SQL gives you: joins, multi-row transactions, and strong consistency. You don't get scale for free — you trade query flexibility and consistency for it. If you later need those back, you rebuild them in application code (badly). Choose the trade deliberately.

Index Internals

An index is a sorted structure — usually a B-tree — that turns a scan into a jump.

◆ B-tree

A shallow, wide, sorted tree. Finding a value is a handful of hops (O(log n)) instead of reading every row (O(n)). Sorted order also serves ORDER BY and range queries for free.

sqlEXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
-- Seq Scan  = reading everything (bad on big tables)
-- Index Scan = jumping straight there (good)
Composite (a,b) helps a and a AND b — not b alone (leftmost prefix) Covering index holds every column the query needs → never touch the table Partial index only some rows (WHERE active = true) → smaller, faster

Clustered vs non-clustered

Clustered the table itself is stored in index order (the primary key in InnoDB). one per table; range scans on it are very fast. Non-clustered a separate structure pointing back to rows. many per table; a lookup may need a second hop to the table.

In MySQL/InnoDB the primary key is the clustered index, so a random UUID PK scatters writes across the table; a sequential id keeps inserts local. In Postgres, tables are heaps and all indexes are secondary — CLUSTER is a one-time reorder.

▲ Indexes aren't free

Each one costs disk and slows every write (insert/update must maintain it). Ten indexes on a hot write table can halve write throughput and bloat storage. Index the columns you filter, join, and sort on — measure with EXPLAIN, and drop indexes nothing uses (pg_stat_user_indexes shows unused ones).

Sharding & Partitioning

⚡ Real problem

One table has 2 billion rows. It no longer fits one machine's memory or disk comfortably.

Split the data across pieces.

Partitioning split ONE database's table into chunks (by date, range) Sharding split across MANY databases/machines (by a shard key)

Choosing a shard key

Hash of id even spread, but range queries hit every shard Range (date) great for time-range queries, but the newest shard is a hotspot Tenant/geo all of one customer's data on one shard — clean isolation

The shard key is the most important — and least reversible — decision. A bad key creates hotspots (one shard does all the work) or forces scatter-gather queries (every read hits all shards).

▲ Sharding is a one-way door

Cross-shard joins and transactions become painful or impossible; unique constraints across shards need coordination; re-sharding is a migration project with downtime risk. Exhaust every cheaper option first — read replicas, aggressive caching, table partitioning, a bigger box. Shard only when a single primary genuinely can't hold the write load, and you've measured it.

Transactions & Isolation

A transaction makes many statements behave as one atomic unit. Isolation levels decide how much concurrent transactions see of each other.

Read Uncommitted sees others' uncommitted writes (dirty reads) Read Committed only committed data (Postgres default) Repeatable Read same query, same result within the txn Serializable as if transactions ran one at a time (safest, slowest)
◆ The anomalies

Dirty read: see uncommitted data. Non-repeatable read: same row changes mid-txn. Phantom: new rows appear matching your filter. Higher isolation removes more anomalies at the cost of concurrency.

php · LaravelDB::transaction(function () {
    $acc = Account::where('id', 1)->lockForUpdate()->first(); // pessimistic
    $acc->balance -= 100;
    $acc->save();
}, attempts: 3); // retry on deadlock
▲ Deadlocks are normal — plan for them

Two transactions lock rows in opposite order and wait on each other forever; the DB kills one with a deadlock error. You don't prevent them entirely — you (1) always acquire locks in a consistent order, (2) keep transactions short, and (3) retry the victim (Laravel's attempts:). A deadlock is a retry signal, not a crash.

▲ Never do slow work inside a transaction

A transaction holds its locks until commit. An HTTP call or email inside DB::transaction() holds those locks for seconds, blocking every other writer and cascading into timeouts. Do external work after commit — or dispatch it to a queue.

DNS

⚡ Real problem

Browsers speak IP addresses. Humans type app.com. Something must translate.

DNS is a distributed lookup: name → IP. It resolves through a hierarchy, cached at every level.

Browser cache→ OS cache→ Resolver (8.8.8.8)→ Root→ TLD (.com)→ Authoritative
Checked fastest-first. Only a miss walks the full hierarchy.
Recursive browser → resolver: "give me the final IP" Iterative resolver → hierarchy: each server points to the next TTL how long an answer may be cached (freshness vs load trade)

The records you'll touch

A / AAAA name → IPv4 / IPv6 CNAME name → another name (alias; app.com → lb.provider.com) MX where email goes TXT verification, SPF/DKIM NS which servers are authoritative for the zone
◆ System-design lever

DNS is the first place traffic is shaped. It can load-balance (return rotating IPs), route users to the nearest region (GeoDNS / Anycast), and fail over (health-checked DNS drops a dead region's IP). CDNs work partly through DNS — your CNAME points at their edge.

▲ TTL is a double-edged failover tool

Low TTL = fast failover (clients re-resolve quickly) but more DNS traffic. High TTL = fewer lookups but a dead IP stays cached for hours. And clients/ISPs often ignore TTLs and over-cache — so DNS is slow, unreliable failover. For fast failover, prefer a load balancer with a stable IP over DNS changes.

HTTP, HTTPS & TLS

HTTP is a stateless request/response text protocol over TCP. HTTPS wraps it in TLS for privacy, integrity, and server identity.

HTTP/1.1 persistent connections; head-of-line blocking HTTP/2 multiplexing (many requests, one connection), binary, header compression HTTP/3 runs on QUIC (UDP) — faster setup, better on bad networks

The TLS handshake

1 ClientHello — versions, cipher suites, key share 2 ServerHello — chosen cipher, certificate, key share 3 both derive a shared secret (ECDHE) → encrypted from here TLS 1.3 does this in ONE round trip.
◆ Three guarantees

Confidentiality (encrypted), Integrity (tamper-evident), Authentication (real server via certificate). Port 80 plain, 443 TLS.

Head-of-line blocking, across versions

HTTP/1.1 one request at a time per connection → browsers open ~6 connections HTTP/2 many streams on ONE connection, but a lost TCP packet stalls ALL streams (HOL blocking moved from app layer down to TCP) HTTP/3 QUIC over UDP — independent streams, a lost packet stalls only its own stream
◆ Idempotency & retries

GET/PUT/DELETE repeated = same final state; POST/PATCH not. This governs retry safety: a proxy or client may safely retry a GET on a dropped connection, but blindly retrying a POST can double-charge. For POSTs that must be retry-safe, use an idempotency key (Module 4).

▲ Don't roll your own TLS or store plaintext

Terminate TLS at a proxy/CDN with a managed certificate (Let's Encrypt auto-renew). Never implement crypto yourself, never log tokens or full card numbers, and redirect all HTTP → HTTPS with HSTS so downgrade attacks can't strip it.

Reverse Proxy & API Gateway

A reverse proxy sits in front of your servers and acts on their behalf. An API gateway is a smarter one for microservices.

Reverse proxy (Nginx) load balancing · TLS termination · caching · compression · hide backends API gateway all of the above + auth · rate limiting · routing to many services · request aggregation · versioning
◆ TLS termination

The proxy decrypts HTTPS and forwards plain HTTP internally — your app servers skip the crypto CPU cost. One place to manage certificates.

▲ Forward vs reverse

Forward proxy acts for the client (hides who's asking — corporate/VPN egress). Reverse proxy acts for the server (hides the backend, spreads load). Same machine role, opposite side of the conversation.

▲ The gateway can become a bottleneck / SPOF

Everything flows through the gateway, so it's a single point of failure and a scaling chokepoint. Run it redundantly, keep per-request work cheap (auth via a fast token check, not a DB call per request), and don't stuff business logic into it — it routes and protects, it doesn't compute.

◆ Client → server IP

Behind a proxy your app sees the proxy's IP, not the user's. The real client IP arrives in X-Forwarded-For. In Laravel, configure TrustProxies so $request->ip() and rate limiting see the true client — otherwise you rate-limit the proxy and lock everyone out together.

CDN & Edge Caching

⚡ Real problem

Server in New York. User in Tokyo. Every image crosses the Pacific — on every request.

A CDN puts copies of your content on edge servers near users worldwide.

Tokyo user→ Tokyo edge (hit)→ served in ms
Only a cache miss travels back to the New York origin.

Controlling what caches, and for how long

http · cache headersCache-Control: public, max-age=31536000, immutable   # hashed asset: cache forever
Cache-Control: no-store                                # /account: never cache
Cache-Control: public, s-maxage=60                     # CDN 60s, browser shorter

The trick for static assets: put a content hash in the filename (app.9f2c.js). Cache it forever; when the content changes the filename changes, so there's no stale-cache problem and no purge needed. This is what Vite/Mix do.

◆ Beyond speed

CDNs also absorb DDoS (traffic hits the edge, not your origin), terminate TLS at the edge, and offload static bytes from your servers. Cache hashed assets aggressively; for dynamic HTML use short s-maxage or explicit purges on publish.

▲ Never cache authenticated responses at the CDN

Caching a page that contains one user's data at a shared edge can serve their data to the next visitor. Mark per-user responses Cache-Control: private, no-store, and vary on auth. A CDN mis-cache of logged-in content is a real, embarrassing data leak.

WebSockets & Real-Time

⚡ Real problem

Chat, live notifications, presence. HTTP is request/response — the server can't push. Polling every second wastes everything.

A WebSocket upgrades one HTTP connection into a persistent, full-duplex TCP pipe. Either side sends anytime.

1 Client sends HTTP with Upgrade: websocket 2 Server replies 101 Switching Protocols 3 TCP stays open; both exchange frames — no new handshakes
▲ No auto-reconnect, no dead-detection

TCP thinks a silent connection is alive. Production needs ping/pong heartbeats to detect dead clients and exponential-backoff reconnection (1→2→4→8s, cap). Reconnecting makes a new socket + restores state.

▲ Scaling connections

100k WebSockets = 100k open sockets + file descriptors, held open idle — not 100k threads. The bottleneck is memory per connection and fan-out, not CPU. Classic PHP-FPM (one process per request) can't hold long-lived connections, which is why WebSocket servers use an event loop.

◆ Laravel: broadcasting + the backplane problem

broadcast(new MessageSent($msg)) pushes an event to connected clients (via Laravel Reverb, an event-loop server, or Pusher). But if users are spread across 3 WebSocket servers, a message on server A must reach subscribers on B and C — that's the backplane: a Redis pub/sub layer all servers subscribe to, so any server can fan a message out to all. Clients receive it with Laravel Echo.

▲ When NOT to use WebSockets

For one-way, infrequent server→client updates, Server-Sent Events (SSE) or simple polling is far cheaper — no persistent bidirectional socket to manage. Reserve WebSockets for genuinely bidirectional, low-latency, high-frequency traffic (chat, live collaboration, trading).

Monolith vs Microservices

⚡ Real problem

"Let's do microservices" — on a 3-person team, before product-market fit.

Monolith one deployable. Simple, fast to build, one DB, easy transactions. Pain: one big codebase, scale all-or-nothing, one deploy risk. Microservices many services. Independent deploy/scale, team autonomy. Pain: network calls, distributed txns, observability, ops load.
◆ The honest default

Start with a well-structured modular monolith — clear internal boundaries, one deployable. Split out a service only when a real boundary and a real scaling/ownership need appear together. Microservices trade code complexity for operational complexity (networks, deploys, monitoring, distributed debugging) — pay that price when you must, not before.

▲ The distributed monolith — worst of both

Split into services that still call each other synchronously for every operation and share a database, and you get microservices' operational pain with a monolith's coupling: one service down takes the rest with it, and you can't deploy independently. If services can't fail and deploy independently, they aren't microservices — they're a monolith with network latency bolted in.

◆ Conway's Law

Systems mirror the org that builds them. Microservices work when you have multiple teams that need to own and ship independently. For one small team, service boundaries just add coordination overhead across a network. Match architecture to team structure.

Message Queues & Async

A queue decouples producers from consumers. Producer drops a message and moves on; a worker handles it later.

Producer (API)→ Queue→ Worker 1Worker 2
Buffers spikes · smooths load · retries on failure · scales consumers independently.
Cuts latency user doesn't wait for slow work Absorbs spikes queue holds the backlog; workers drain at their pace Decouples producer and consumer scale and fail independently

Delivery semantics

At-most-once fire and forget — may lose messages, never duplicates At-least-once retry until acked — never lost, MAY duplicate (the common default) Exactly-once the holy grail — expensive, and often really "at-least-once + idempotency"
▲ At-least-once means duplicates will happen

A consumer processes a message, then crashes before sending its ack — the broker re-delivers to someone else. So "exactly-once" in practice = at-least-once delivery + idempotent consumers (dedupe by message id). Design every consumer to survive seeing the same message twice, or you double-charge, double-email, double-ship.

▲ Ordering isn't guaranteed across a queue

With multiple consumers pulling in parallel, messages finish out of order. If order matters (events for one account), partition by a key so all related messages go to one consumer in sequence — the same idea as a Kafka partition key.

Event-Driven Architecture

Services don't call each other directly. They emit events ("OrderPlaced") to a broker; interested services subscribe.

◆ Why

Add a new consumer (fraud check, loyalty points) without touching the order service. Loose coupling, independent scaling. The cost: eventual consistency and harder debugging (trace an event across services).

Queue point-to-point, one consumer takes each message (work distribution) Pub/sub broadcast, every subscriber gets a copy (event fan-out)

The distributed-transaction problem: Sagas

Order service, Payment service, Inventory service — each with its own database. There's no cross-service DB::transaction(). So how do you "charge and reserve stock, or neither"?

A Saga: a sequence of local transactions, each emitting an event that triggers the next. If a step fails, run compensating actions to undo the earlier ones (refund the charge, release the stock).

OrderCreated → ChargeCard → ReserveStock → Confirm if ReserveStock fails → RefundCard (compensate) → CancelOrder
▲ Events trade consistency for coupling

Event-driven systems are eventually consistent — for a moment, the order exists but stock isn't reserved yet. And debugging is harder: a single user action becomes a trail of events across services, so you need distributed tracing (Module 5) to follow it. You buy loose coupling and independent scaling by paying in consistency and observability.

Kafka Internals

Kafka is a distributed, append-only log. Not a "queue that deletes on read" — a durable, replayable stream.

Topic named stream, split into partitions Partition ordered, append-only log; unit of parallelism Offset a consumer's position in a partition Consumer group partitions divided across group members
◆ Why it's different

Messages aren't deleted when read — they stay for a retention window. Consumers track their own offset, so you can replay history, add new consumers that read from the start, and get massive throughput via partitioning. Order is guaranteed within a partition, not across.

▲ Partition key choice

Same key → same partition → ordered. Pick a key that spreads load evenly but keeps related events together (e.g. user_id). A skewed key (one whale user, or a null key) makes one partition a hotspot while others idle.

Consumer groups & parallelism

Partitions are the unit of parallelism: a topic with 6 partitions can be read by up to 6 consumers in a group, one partition each. Add a 7th consumer and it sits idle. So partition count caps your consumer parallelism — choose it with headroom.

▲ Rebalancing pauses everything

When a consumer joins or leaves, Kafka rebalances — reassigns partitions across the group, briefly pausing consumption. Frequent crashes/restarts cause constant rebalances and lag. Keep consumers stable and tune session timeouts.

◆ Kafka vs RabbitMQ, sharply

RabbitMQ: a smart broker — routes, and messages vanish once acked. Great for task queues and complex routing. Kafka: a dumb, durable log — consumers track their own offset and can replay. Great for event streaming, analytics, and multiple independent consumers of the same stream.

Idempotency & Rate Limiting

Idempotency

An operation you can repeat safely with the same result. Essential because networks retry.

php · idempotency key// client sends a unique key; server does the work once
if (Cache::has("idem:$key")) return Cache::get("idem:$key");
$result = $this->charge($order);
Cache::put("idem:$key", $result, now()->addDay());
return $result;

Rate limiting

Token bucket refill tokens over time; each request spends one (allows bursts) Fixed window N requests per minute (simple; boundary bursts) Sliding window smooth rolling count (fairer)
▲ Idempotency key: reserve before you work

The subtle bug: two identical requests arrive at once, both see "no key yet," both charge. Fix by atomically claiming the key first (SET key ... NX — set-if-not-exists). The winner processes; the loser returns the in-progress/cached result. The key must be stored transactionally with the side effect, or a crash between them re-charges.

◆ Laravel rate limiting

RateLimiter::for('api', fn($r) => Limit::perMinute(60)->by($r->user()?->id ?: $r->ip())). Returns 429 with a Retry-After header when exceeded. It's Redis-backed, so the limit is shared across every app server — limiting per-instance would let N servers allow N× the traffic. Key by user id when authenticated, IP otherwise.

Redundancy & Failover

No single machine is trustworthy. Reliability = no single point of failure.

Redundancy run 2+ of everything (app, DB, LB, region) Failover when one dies, another takes over automatically SPOF single point of failure — the thing to hunt and eliminate
▲ The load balancer is a SPOF

You added the LB to remove SPOFs — now it's one. Run redundant LBs with a floating/virtual IP that fails over. The DB primary is another: use a replica that can be promoted.

Active-active vs active-passive

Active-passive standby sits idle, takes over on failure ✅ simple ❌ paying for idle capacity, failover has a gap Active-active all nodes serve traffic; one dying just sheds its share ✅ no idle cost, instant absorption ❌ needs stateless design + sync
◆ Nines cost exponentially

99.9% = ~8.7h downtime/year. 99.99% = ~52min. 99.999% = ~5min. Each nine multiplies cost — redundant everything, multi-region, automated failover, on-call. Pick the target the product and revenue actually justify; don't chase five nines for a blog.

▲ Test your failover, or it doesn't exist

A standby you've never failed over to is a standby you don't know works. Backups you've never restored are Schrödinger's backups. Run game days / chaos drills — kill a node in production-like conditions and confirm the system actually survives.

Timeouts, Retries & Circuit Breakers

⚡ Real problem

A downstream API hangs. Your requests pile up waiting. Threads exhaust. Your whole app goes down — because their service was slow.

Timeout never wait forever; fail fast Retry + backoff retry transient failures, spaced out + jitter Circuit breaker after N failures, stop calling for a while → fail instantly
Closed (normal)→ failures → Open (reject fast)→ wait → Half-open (test)
The breaker stops a slow dependency from dragging you down with it.

Bulkheads & timeout budgets

Bulkhead (from ship design): isolate resources per dependency so one drowning call can't sink everything. Give the flaky recommendations API its own small connection pool — when it hangs, it exhausts its pool, not your whole app's threads.

Timeout budget: if the user's request has 3 seconds and it fans out to 3 services, each can't wait 3 seconds. Budget the total across the chain, or one slow leaf blows the whole request.

▲ Retries can cause the outage

A service gets slow; every caller retries; the retries triple the load and finish it off — a retry storm / thundering herd. Always add jitter (randomized backoff), a hard retry cap, and a circuit breaker so retries stop entirely once a service is clearly down. Retries without these amplify failures instead of absorbing them.

Observability

You can't fix what you can't see. Three pillars.

Logs discrete events — "what happened" (structured, searchable) Metrics numbers over time — "how much / how fast" (p95, error rate, QPS) Traces one request across services — "where did the time go"
◆ Metrics find it, traces locate it, logs explain it

A metric alert (p95 spiked) tells you something is wrong. A distributed trace shows which service/span is slow. Logs on that span tell you why. Use all three together.

Correlation IDs — the thread through the maze

Attach a unique request_id at the edge and pass it through every service, log line, and job. Now one grep reassembles a single user's journey across the whole system. Without it, distributed logs are noise.

◆ Golden signals

Latency, Traffic, Errors, Saturation. Dashboard these four per service and you catch most problems before users do. Alert on symptoms users feel (error rate, p95) — not on causes (CPU 80% might be totally fine).

◆ SLI / SLO / error budget

SLI = the measured number (99.95% of requests < 300ms). SLO = the target (99.9%). The gap is your error budget — how much unreliability you're allowed. Budget left → ship features faster. Budget spent → stop and fix reliability. It turns "how reliable?" into a number both engineers and product agree on.

Graceful Degradation

When part of the system fails, the whole product shouldn't. Degrade a feature, keep the core alive.

Recommendations down → show popular items instead of erroring Search slow → serve cached results, hide filters Payments flaky → queue the order, confirm async
◆ Bulkheads + fallbacks

Isolate failures (separate pools/limits per dependency = bulkheads) so one drowning feature can't sink the ship. Give each risky call a fallback — a default value, a stale cache, or a queued retry — so a dependency being down degrades one feature instead of erroring the page.

◆ Feature flags & load shedding

Feature flags let you turn off an expensive or broken feature instantly, without a deploy — your emergency valve under load. Load shedding goes further: when overwhelmed, deliberately reject low-priority traffic (return 503 to background/anonymous requests) so paying users still get served. Serving 90% of users well beats serving 100% a timeout.

▲ Fail static, not blank

If personalization is down, show generic popular content — not an error. A degraded page that still works keeps users and buys you time to fix the root cause. Design each feature to have a "reduced but functional" mode.

PHP Request Lifecycle & FPM

⚡ Real problem

People think PHP is "slow" or "dead." They don't know how it actually runs — and why the shared-nothing model is a strength.

PHP's model: each request starts fresh, runs, and throws everything away. No shared memory between requests. Simple and crash-isolated.

Nginx→ PHP-FPM pool→ worker process→ run script→ reset
FPM keeps a pool of worker processes; each handles one request at a time, then resets.
SAPI how PHP is invoked: FPM, CLI, mod_php FPM worker a PHP process handling one request at a time Shared-nothing request state dies at the end — no leaks across requests

Tuning the worker pool

pm = static fixed N workers — predictable memory, best for dedicated boxes pm = dynamic scale workers between min/max with load — general default pm = ondemand spawn only on request — low-traffic / many-sites boxes max_workers ≈ available_RAM / avg_worker_memory

If each worker uses ~60MB and you have 4GB free, ~60 workers is the ceiling. Set it higher and traffic spikes trigger the OOM killer — which takes down more than it saves.

◆ Why this matters for scaling

Concurrency = number of FPM workers. Too few → requests queue behind busy workers (latency climbs). Too many → RAM exhausted → OOM. And each worker opens DB connections, so workers × servers can blow past Postgres max_connections — put PgBouncer between them. Sizing the pool is the core PHP performance lever.

▲ One slow endpoint starves the pool

If a slow report ties up workers for 10s each, they're unavailable for fast requests — the whole site feels down though CPU is idle (workers are just waiting). Move slow/blocking work to a queue so request workers stay free.

Opcache, Memory & GC

Opcache

PHP compiles source to opcodes on every request — wasteful. Opcache stores the compiled opcodes in shared memory, so the compile happens once.

◆ Non-negotiable in production

Enabling opcache is often a 2–3× throughput win for free. opcache.enable=1, tune memory_consumption and max_accelerated_files.

Memory & garbage collection

PHP uses reference counting + a cycle collector. Each request has a memory_limit. Because state is thrown away per request, leaks rarely accumulate — the process resets.

Preloading & JIT

Preloading (PHP 7.4+): load your framework's hot classes into opcache shared memory once at server start, so they're never re-read per request. JIT (PHP 8+): compile hot opcodes to machine code — a real win for CPU-bound math, but marginal for typical I/O-bound web requests (which wait on DB, not CPU).

▲ Long-running processes flip the rules

Shared-nothing safety exists because FPM resets per request. Queue workers and Octane don't reset — so memory leaks, growing static arrays, and stale singletons accumulate across requests. Restart workers periodically (--max-jobs=1000, --max-time=3600) and audit for state that outlives a request.

Concurrency in PHP

⚡ Real problem

"PHP can't do concurrency" — half-true, and worth understanding precisely.

Classic PHP is synchronous and single-threaded per request. Concurrency comes from running many processes (FPM workers), not threads inside one.

Process model N FPM workers = N concurrent requests (the normal way) Async runtimes Swoole / Octane / ReactPHP — event loop, coroutines, persistent state Parallel real threads via ext-parallel (rare)

Concurrency within one request

Even classic PHP can overlap I/O. Need 3 independent HTTP calls? Fire them concurrently instead of one-after-another.

php · Guzzle concurrent requests$responses = Http::pool(fn($pool) => [
    $pool->get('https://a.com'),
    $pool->get('https://b.com'),
    $pool->get('https://c.com'),
]);   // ~1× the slowest call, not the sum of all three

PHP 8.1 Fibers add cooperative multitasking primitives — the foundation async libraries (ReactPHP, Amp) build on.

◆ The shift with Octane / Swoole

They keep the app booted in memory across requests (no per-request bootstrap = big latency win) and add an event loop for true async. The cost: you lose shared-nothing safety — leaked globals, stale singletons, and request state on long-lived objects become real bugs. It's more speed for more discipline.

Service Container & Providers

The container is Laravel's core: an object factory that resolves classes and their dependencies via reflection.

php$app->bind(PaymentGateway::class, StripeGateway::class);   // interface → impl

// type-hint anywhere → resolved + injected automatically

bind new instance each resolve singleton one shared instance contextual "class A gets S3, class B gets local" register() providers bind here · boot() providers use services here
▲ singleton state under Octane

Under normal PHP a singleton lives one request, so holding a little state is harmless. Under Octane the singleton persists across requests — stashing the current user or request on it leaks one user's data into the next. Bind request-scoped things with scoped(), not singleton().

◆ Why it's the heart

It makes Dependency Inversion cheap: depend on interfaces, swap implementations (real ↔ fake, Stripe ↔ PayPal) with one binding. Every Laravel subsystem — router, Eloquent, cache, queue, mail — is resolved through it. Master the container and the whole framework becomes legible.

Laravel Request Lifecycle

public/index.php ↓ bootstrap/app.php — build the Application (container) ↓ Http/Kernel::handle() ↓ global + route middleware (Pipeline) ↓ Router::dispatch — match route Controller (resolved from container) ↑ Response back up through middleware → Browser
◆ Middleware = Pipeline = onion

Laravel's Pipeline wraps each middleware around the next as nested closures. Auth, throttle, CSRF, CORS all live here. It's the Chain of Responsibility pattern — each layer handles the request or passes it on, and can act on the way out too.

▲ Bootstrap cost & caching

Every request boots the framework: load env, merge config, register all providers. In production, cache it — config:cache, route:cache, event:cache, and optimize — to skip that work. Forget these and each request pays the full bootstrap tax. (But config:cache means env() returns null outside config files — a classic gotcha.)

◆ Terminable middleware

Middleware with a terminate() method runs after the response is sent to the browser — perfect for logging or session writes that shouldn't delay the user. It's how Laravel does "respond now, clean up after."

Eloquent & the N+1 Problem

Active Record ORM. The magic is __callStatic forwarding to a query Builder that compiles SQL lazily.

php// ❌ N+1: 1 + 100 queries
foreach (Post::all() as $p) echo $p->author->name;
// ✅ eager load: 2 queries total
Post::with('author')->get();

Memory: stream large result sets

Post::all() on a million rows hydrates a million objects into RAM and OOMs the worker. Stream instead:

phpOrder::query()->lazy()->each(fn($o) => process($o));  // generator, low memory
Order::chunk(1000, fn($rows) => ...);                // 1000 at a time
Order::toBase()->get();                               // plain rows, no model hydration
▲ Catch N+1 before it ships

Model::preventLazyLoading(!app()->isProduction()) in AppServiceProvider::boot() throws when a relation lazy-loads — a silent 200-query page becomes a loud dev exception. Pair with Debugbar/Telescope. This one line stops the most common Laravel performance bug from ever reaching production.

◆ Other Eloquent perf tools

withCount('comments') instead of loading and counting; select() only needed columns; cursor() for read-only streaming; database-level chunkById for safe batch updates. Most "Eloquent is slow" is really "loading too much."

A long-running worker keeps the old code in memory after you deploy. Run queue:restart in your deploy script so workers gracefully finish the current job and reload. Under Supervisor, workers that crash are auto-restarted — Horizon manages all of this (auto-scaling worker counts, metrics, failure dashboard) and is the standard for Redis queues.

Octane & Performance

Octane boots Laravel once and keeps it in memory (Swoole/FrankenPHP), serving requests from the warm app — no per-request bootstrap.

Normal PHP boot framework → handle request → throw away (every request) Octane boot once → handle many requests from memory (much faster)
▲ Shared-nothing is gone

Static properties, singletons holding request data, and container state now persist between requests. Leaked state = cross-request bugs. Audit for globals; reset per-request state.

The performance checklist

opcache on · route/config/view cache · eager-load (kill N+1) Redis cache + sessions · queue slow work · DB indexes + read replicas CDN for assets · PgBouncer for connections · Octane when you need more
▲ The Octane discipline checklist

Before enabling Octane, audit for cross-request leaks: no request/user data on singletons, reset static properties, don't hold DB results in globals, and use scoped() bindings for per-request services. Octane's speed comes from not resetting — which is exactly what makes leaked state dangerous.

Requirements & Estimation

⚡ The interview prompt

"Design a URL shortening service like bit.ly." — Before you draw a single box, pin down what the system does and how much it handles. Every design decision flows from these numbers.

Functional requirements

Core 1. Given a long URL → return a short URL (e.g. short.ly/abc123) 2. Given a short URL → redirect to the original (301/302) 3. Short links expire after a configurable TTL (default: 5 years) 4. Custom aliases: user may pick their own short code Nice to have 5. Analytics: click count, referrer, geo, device 6. Rate limiting per user/IP 7. API access with auth tokens

Non-functional requirements

Availability very high — a redirect that's down = every short link on the internet is broken Latency redirect must be fast (< 50ms p99) — user is waiting for a page load Read-heavy 100:1 read-to-write ratio — people click links far more than they create them Durability once created, a link must work until it expires — no silent data loss

Back-of-envelope estimation

Writes 100M new URLs / month ≈ ~40 URLs/sec Reads 100:1 ratio → 10B redirects / month ≈ ~4,000 reads/sec Storage each record ~500 bytes (URL + metadata) 100M × 500B × 12 months × 5 years ≈ 3 TB total Cache 80/20 rule — 20% of URLs get 80% of traffic 20% of daily URLs in cache → manageable in Redis
◆ Why estimation matters

These numbers tell you: a single Postgres can handle 40 writes/sec easily. 4,000 reads/sec needs a cache layer. 3TB is big but not sharding-mandatory. Start simple, scale where the numbers demand.

◆ Interview tip

Always state your assumptions out loud: "I'll assume 100M new URLs per month" — the interviewer will correct you if they want different numbers. The process of estimation matters more than exact figures.

Key Generation — The Core Algorithm

⚡ The hard problem

How do you generate a unique 6–7 character code for each URL? It must be unique, unguessable, and fast to generate at scale. This is the heart of the system.

Option 1: Hash + truncate

How MD5/SHA256 the long URL → take first 7 characters → base62 encode Pro same URL always gives same hash → natural dedup Con collisions — two different URLs can hash to the same 7 chars Fix on collision, append a counter and re-hash, or probe next slot
php// hash approach
$hash = md5($longUrl);                // 32 hex chars
$code = substr(base_convert($hash, 16, 36), 0, 7);
▲ Hash collision is a real problem

With 7 chars of base62, you have 62⁷ ≈ 3.5 trillion combinations. But by the birthday paradox, collisions start appearing around √(3.5T) ≈ 1.87M URLs. You must check for collisions and handle them — either retry with a salt or use a different approach entirely.

Option 2: Counter-based (auto-increment)

How auto-increment ID (1, 2, 3...) → base62 encode Pro zero collisions, simple Con predictable — user can guess next URL (security risk) single point of failure if one DB generates IDs Fix add random padding, or use a distributed counter
php// counter approach
function toBase62(int $num): string {
    $chars = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
    $result = '';
    while ($num > 0) {
        $result = $chars[$num % 62] . $result;
        $num = intdiv($num, 62);
    }
    return $result ?: '0';
}
// toBase62(1000000) → "4c92"

Option 3: Pre-generated key pool (KGS) ★

How a Key Generation Service pre-generates millions of unique random codes stores them in a DB table with two columns: key, used (boolean) on create-request → grab next unused key, mark it used Pro no collision checks at write time — keys are guaranteed unique no predictability — keys are random scales horizontally — multiple servers can grab keys from the pool Con need to manage the key pool — refill when running low if a server grabs a key and crashes, that key is "wasted" (acceptable)
KGS daemon→ key_pool table→ App grabs batch→ Assign to URL
Keys are pre-generated in background. App servers grab batches (e.g. 1000 at a time) into local memory.
sql-- Key pool table
CREATE TABLE key_pool (
    code     CHAR(7) PRIMARY KEY,
    used     BOOLEAN DEFAULT FALSE,
    used_at  TIMESTAMP NULL
);

-- Grab a batch atomically
UPDATE key_pool SET used = TRUE, used_at = NOW()
WHERE code IN (
    SELECT code FROM key_pool WHERE used = FALSE LIMIT 1000
    FOR UPDATE SKIP LOCKED
)
RETURNING code;
◆ KGS is the go-to answer in interviews

It separates key uniqueness from the write path. No race conditions on the hot path. Pre-generation is a background job. And FOR UPDATE SKIP LOCKED lets multiple app servers grab keys concurrently without blocking each other — this is a real PostgreSQL feature you should know.

Base62 math

Base62 [0-9a-zA-Z] = 62 characters 6 chars 62⁶ = 56.8 billion combinations 7 chars 62⁷ = 3.5 trillion combinations At 100M URLs/month: 6 chars last ~47 years 7 chars last ~2,900 years 6 characters is enough. 7 gives room to breathe.

Database Schema & Storage

Two tables run the whole system. One for URLs, one for analytics events.

Core schema

sqlCREATE TABLE urls (
    code        CHAR(7)      PRIMARY KEY,
    long_url    TEXT         NOT NULL,
    user_id     BIGINT       NULL,        -- nullable for anonymous
    created_at  TIMESTAMP    NOT NULL DEFAULT NOW(),
    expires_at  TIMESTAMP    NOT NULL,
    click_count BIGINT       NOT NULL DEFAULT 0
);

-- For looking up by long URL (dedup check)
CREATE INDEX idx_urls_long ON urls (long_url) USING hash;

-- For expiry cleanup
CREATE INDEX idx_urls_expires ON urls (expires_at) WHERE expires_at IS NOT NULL;
◆ Why code is the PK, not an auto-increment ID

The short code is the lookup key. Every redirect query is WHERE code = ?. Making it the primary key means the lookup is a single clustered-index scan — no secondary index hop. One disk seek for the hottest query in the system.

Analytics events table

sqlCREATE TABLE clicks (
    id          BIGSERIAL PRIMARY KEY,
    code        CHAR(7)      NOT NULL,
    clicked_at  TIMESTAMP    NOT NULL DEFAULT NOW(),
    ip          INET,
    country     CHAR(2),
    referrer    VARCHAR(500),
    user_agent  VARCHAR(500)
);

-- For per-URL stats
CREATE INDEX idx_clicks_code ON clicks (code, clicked_at);
▲ Clicks table grows fast — plan for it

At 10B clicks/month, this table grows by ~120B rows/year. Options: (1) partition by month — PARTITION BY RANGE (clicked_at), drop old partitions. (2) Move to a time-series DB (TimescaleDB, ClickHouse). (3) Write clicks to Kafka first, aggregate in batch, store only summaries in Postgres.

SQL vs NoSQL — what fits here?

URLs table simple key→value lookup, fits both SQL and NoSQL SQL: strong consistency, ACID, easy joins for user dashboard NoSQL (DynamoDB): insane read throughput, auto-sharding by code Clicks table append-only, time-series data PostgreSQL + partitioning works until ~1B rows Beyond that: ClickHouse or TimescaleDB Verdict start with PostgreSQL for everything. Move clicks to a columnar store when volume demands it.
◆ Schema reflects the access pattern

URL lookups are by code (PK scan). Click inserts are append-only (fast). Click reads are by code + time range (composite index). Hash index on long_url for dedup. Every index serves exactly one query pattern — no wasted indexes.

Read & Write Flow

Two flows. Write is rare (40/sec). Read is everything (4,000/sec). Optimize accordingly.

Write flow: creating a short URL

Client POST→ Rate limit check→ Grab key from pool→ Insert URL row→ Return short URL
Write path: validate → get unique code → store → respond. ~40 writes/sec — Postgres handles this trivially.
php — write flowpublic function create(StoreUrlRequest $request): JsonResponse
{
    // 1. Check if this URL was already shortened (dedup)
    $existing = Url::where('long_url', $request->long_url)
                   ->where('user_id', $request->user()?->id)
                   ->first();

    if ($existing) {
        return response()->json($existing, 200);
    }

    // 2. Grab a pre-generated key
    $code = $this->keyPool->take();

    // 3. Insert
    $url = Url::create([
        'code'      => $code,
        'long_url'  => $request->long_url,
        'user_id'   => $request->user()?->id,
        'expires_at' => $request->expires_at ?? now()->addYears(5),
    ]);

    // 4. Warm the cache
    Cache::put("url:{$code}", $url->long_url, $url->expires_at);

    return response()->json($url, 201);
}

Read flow: redirecting

GET /abc123→ Cache lookup→ Hit? Redirect
Cache miss→ DB lookup→ Fill cache→ Redirect
Read path: cache first → DB fallback → warm cache → redirect. Target: <10ms for cache hit.
php — read flowpublic function redirect(string $code): RedirectResponse
{
    // 1. Cache first
    $longUrl = Cache::get("url:{$code}");

    if (!$longUrl) {
        // 2. DB fallback
        $url = Url::where('code', $code)
                  ->where('expires_at', '>', now())
                  ->first();

        if (!$url) {
            abort(404);
        }

        $longUrl = $url->long_url;

        // 3. Warm cache for next hit
        Cache::put("url:{$code}", $longUrl, $url->expires_at);
    }

    // 4. Track click asynchronously (don't slow down redirect)
    TrackClick::dispatch($code, request());

    return redirect($longUrl, 302);
}
◆ The critical insight: async analytics

Never make the user wait for analytics to be written. The redirect returns immediately. The click event goes to a queue (Redis/SQS) and a worker writes it to the clicks table in the background. User sees <10ms redirect; analytics arrive seconds later. Acceptable trade-off.

▲ Cache stampede on popular links

If a viral link's cache entry expires, thousands of concurrent requests all miss the cache and hit the DB simultaneously. Solutions: (1) Use Cache::lock() — only one request rebuilds the cache, others wait. (2) Set cache TTL to be much longer than link TTL and check expiry in app logic. (3) Warm cache proactively for high-traffic links.

Caching Strategy

Cache makes this system fast. Without it, you're hitting the DB 4,000 times/sec for the same popular links over and over.

What to cache

URL mapping code → long_url (the redirect lookup) key: url:{code} value: the long URL string TTL: match the link's expiry date Click counts code → total click count key: clicks:{code} Redis INCR for real-time counter Flush to DB periodically (every 5 min or every 100 clicks) NOT cached individual click events (they go to queue → DB) user dashboards (low traffic, always fresh from DB)

Cache sizing

80/20 rule: 20% of URLs get 80% of traffic Daily URLs 100M / 30 = ~3.3M URLs/day Hot set 20% = ~660K URLs in cache Avg size ~300 bytes per entry (code + long URL) Total 660K × 300B ≈ ~200 MB in Redis — trivial
Request→ Redis (200MB)→ ~95% hit rate
5% miss→ PostgreSQL→ fill Redis
With a ~95% cache hit rate, Postgres handles only ~200 reads/sec instead of 4,000.

Cache-aside pattern (what we're using)

patternRead path:
1. Check cache
2. Miss → read DB
3. Write result to cache
4. Return

Write path:
1. Write to DB
2. Write to cache (or invalidate cache key)

This is Cache-Aside (Lazy Loading).
Simple, fits read-heavy workloads perfectly.
◆ Why not write-through?

Write-through (write to cache and DB together on every write) works here too, and we do warm the cache on create. But cache-aside is the mental model — because the real value is on the read path, not the write path. Most URLs are created once and read millions of times. Cache-aside naturally populates the cache with what's actually popular.

▲ Cache invalidation on delete

When a user deletes a short URL, you must also Cache::forget("url:{$code}"). If you don't, deleted links keep redirecting from cache until TTL expires. Sounds obvious — gets missed in production constantly.

Analytics & Click Tracking

⚡ The tension

You want rich analytics (every click tracked with geo, device, referrer) but you can't slow down the redirect. The redirect is the product — analytics is a feature. Never sacrifice the product for a feature.

Architecture: async event pipeline

Redirect happens→ Dispatch job→ Queue (Redis)→ Worker processes
Worker→ Parse IP → geo→ Parse UA → device→ INSERT clicks row
Click tracking is fire-and-forget from the redirect's perspective. Workers handle the heavy lifting.
php — TrackClick jobclass TrackClick implements ShouldQueue
{
    public function __construct(
        public string $code,
        public string $ip,
        public ?string $referrer,
        public ?string $userAgent,
    ) {}

    public function handle(): void
    {
        Click::create([
            'code'       => $this->code,
            'ip'         => $this->ip,
            'country'    => geoip($this->ip)->country_code,
            'referrer'   => $this->referrer,
            'user_agent' => $this->userAgent,
        ]);

        // Increment real-time counter in Redis
        Cache::increment("clicks:{$this->code}");
    }
}

Real-time counter vs accurate count

Redis INCR fast, real-time, but volatile (restarts lose count) DB count SELECT COUNT(*) from clicks WHERE code = ? — accurate but slow Hybrid Redis for real-time display, periodic sync to urls.click_count a scheduled job every 5 minutes: UPDATE urls SET click_count = (SELECT COUNT(*) FROM clicks WHERE code = urls.code)
◆ Batch inserts for high-traffic links

At 4,000 clicks/sec, inserting one row per click overwhelms Postgres. Batch: collect clicks in Redis lists (RPUSH clicks:buffer {json}), a worker pops batches of 500 every second and bulk-inserts them. Drops from 4,000 INSERTs/sec to 8 bulk INSERTs/sec.

Aggregation for dashboards

sql-- Pre-aggregate daily stats (run via scheduled job)
INSERT INTO click_stats_daily (code, date, clicks, unique_ips)
SELECT code,
       clicked_at::date,
       COUNT(*),
       COUNT(DISTINCT ip)
FROM clicks
WHERE clicked_at >= CURRENT_DATE - INTERVAL '1 day'
  AND clicked_at < CURRENT_DATE
GROUP BY code, clicked_at::date
ON CONFLICT (code, date) DO UPDATE SET
    clicks = EXCLUDED.clicks,
    unique_ips = EXCLUDED.unique_ips;
◆ Three-tier analytics pattern

Hot: Redis counters (real-time, approximate). Warm: pre-aggregated daily stats table (fast dashboard queries). Cold: raw clicks table (drill-down, partitioned by month, oldest months moved to cold storage). This pattern works for any analytics system, not just URL shorteners.

Rate Limiting & Security

An open URL shortener without rate limiting is a spam cannon. Lock it down.

Rate limiting strategy

Anonymous creates 10 URLs / hour / IP Authenticated creates 100 URLs / hour / user Redirects no limit (it's the product) API reads 1,000 / hour / token Algorithm sliding window counter in Redis key: ratelimit:{user_id}:{minute} INCR + EXPIRE 60
php — Laravel rate limiting// In RouteServiceProvider or route definition
Route::post('/api/v1/urls', [UrlController::class, 'create'])
    ->middleware('throttle:100,60');  // 100 requests per 60 minutes

// Custom rate limiter for more control
RateLimiter::for('url-create', function (Request $request) {
    return $request->user()
        ? Limit::perHour(100)->by($request->user()->id)
        : Limit::perHour(10)->by($request->ip());
});

Security concerns

Malicious URLs shortener can hide phishing/malware links → check against Google Safe Browsing API on create → scan asynchronously, flag suspicious Spam / abuse bots mass-creating links → rate limiting + CAPTCHA on anonymous creates → require email verification for API tokens Enumeration attacker iterates all short codes (abc000 → abc999) → random codes (not sequential) prevent this → KGS approach already solves this Open redirect attacker uses your domain's trust for phishing → display interstitial "you're leaving" page for flagged URLs → report/block mechanism for users
▲ Your domain's reputation is on the line

When someone shortens a phishing link through your service, the phishing email contains your domain. Email filters learn to flag your domain. Google may flag your domain. Abuse prevention isn't a nice-to-have — it's existential for a URL shortener.

◆ Laravel gives you most of this

Rate limiting: built-in throttle middleware backed by Redis. Input validation: FormRequest classes. HTTPS: enforce in AppServiceProvider with URL::forceScheme('https'). Auth: Sanctum for API tokens. You don't need to build these — you need to configure them correctly.

Start simple, scale where the numbers demand. Not before.

Stage 1: single server (handles more than you think)

Nginx→ Laravel app→ PostgreSQL
Redis (cache + queue)
One server. Handles ~1,000 req/sec with Redis caching. Enough for most startups.

Stage 2: separate concerns

Load Balancer→ App Server 1
→ App Server 2
Redis Cluster Postgres Primary→ Read Replica
Multiple app servers behind LB. Redis and Postgres on dedicated machines. Read replica handles analytics queries.

Stage 3: global scale

Sharding shard urls table by code's first character (a-z, 0-9) or use consistent hashing across DB nodes each shard handles ~100M URLs independently CDN cache 301 redirects at the edge (CloudFlare) popular links never reach your server downside: lose analytics for cached redirects Multi-region deploy app servers in US, EU, Asia DNS routes users to nearest region each region has its own Redis + read replica writes go to primary in one region KGS scaling each region pre-fetches key batches from central KGS if region loses connectivity, it has local keys to survive
◆ When to move to each stage

Stage 1→2: when CPU or memory on single server > 70% sustained, or you need zero-downtime deploys. Stage 2→3: when latency from one region is unacceptable (>200ms for users in Asia when servers are in US), or when a single Postgres can't handle the write volume.

◆ Don't shard until you must

A single PostgreSQL with proper indexes handles millions of rows and thousands of reads/sec. Sharding adds operational complexity (migrations, backups, monitoring per shard). At 100M URLs/month, you hit sharding need after ~2-3 years with aggressive growth. Start with one DB, add read replicas, shard last.
